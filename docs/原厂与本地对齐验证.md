# 原厂与本地对齐验证

本轮分两组验证：真实本地序号11及其原厂来源窗口；两边分别新建的独立测试窗口。账号观测仅保存在本机加密台账，公开报告不含账号、Cookie值、代理凭据或密钥。

## 序号11：真实资料对照

按本地保存的来源标识查找同一个原厂窗口，校验身份后完整备份两个关闭的资料目录。来源序号与本地序号独立，不靠同名或同序号猜测对应关系。

| 比较项 | 最终实际结果 |
|---|---|
| 浏览器版本 | 两边均为已核实的148精确构建 |
| 指纹 | 46项全部一致，两次采样均无不稳定项 |
| 附加权限、插件等 | 修复剪贴板初始化后，采样项全部一致 |
| 原有网页 | 原厂4个网址在本地全部保留；本地另有1个按要求显示的IP信息页 |
| Cookie | 35个共有Cookie的值、HTTPOnly及会话属性，在初始、运行75秒后及对应的重开状态均一致；本地额外1条来自IP信息页 |
| 平台本地存储 | 93个键全部保留；7个按键名识别的账号相关项，解析JSON后值全部一致 |
| 实际页面状态 | 检查到的页面两边都未出现密码输入框、登录失效提示或此前的流量异常提示；未提交网站业务操作 |
| 连续运行与重开 | 两边持续75秒；本地再次正常关闭、打开后，46项及共有Cookie值仍一致 |
| 原指纹与基线 | 原生配置和原环境基线均未改变 |

其他本地存储值存在运行时间、数值及编码串变化，不能把这些网页运行产物强制覆盖成另一实例的值。Cookie运行中也出现两边同一条会话属性同步变化；报告按相同阶段比较，保留网页最新资料。

本地与原厂仍有两项运行策略差别：本地按既定要求保证指定代理全局生效；已导入窗口保留备份时的运行种子，原厂可能每次取得更新后的种子。本轮实际网页信号一致，不为追求配置字节相同而重算已有指纹。

打开速度仍有差距。修复前两次普通样本，本地约8.4–8.8秒，原厂约2.3–3.6秒；本次含一次性Cookie备份/迁移为14.8秒。样本受代理及同时进行的测试影响，不是吞吐基准。本地保留环境、资料和代理检查，这些检查存在额外耗时。

证据：`analysis/reports/window11-stock-local-parity-before.json`、`window11-stock-local-parity.json`。

## 新建窗口：已修复的实际差异

| 原问题 | 修复结果 |
|---|---|
| 新建首开与重开的剪贴板初始化混在一起 | 首开默认询问，成熟资料按保存开关初始化；显式禁用从首次生效 |
| 端口保护启用/关闭标签对应值相反 | 标签与原厂值一致，已有记录值不翻转 |
| 移动设备仍套桌面屏幕参数 | 使用原厂公开移动屏幕字典、500×950窗口及对应DPR |
| 所填窗口大小未用于首次打开 | 首次实际边界及网页outer尺寸生效，之后保留用户调整的窗口状态 |
| 移动随机分辨率选到桌面尺寸 | 使用对应设备字典，同指纹批量只固定一次选择 |
| 缺少原厂默认Canvas/WebGL例外规则 | 新建带入已核实的33条完整规则；已有窗口原规则保留 |
| 新建缺少对应版本公开运行种子 | 对内核和完整UA取得、验签并加密缓存；旧载荷继续保留原值 |
| WebRTC替换模式未单独触发出口取得 | 即使其他按IP项关闭也取得出口，正式代理门禁核对后才打开 |
| 空位置变成0或字段类型不一致 | 对齐原厂空值及缺失字段，保留明确填写的有效0 |
| 自动环境检查挡住到期签名维护 | 先维护签名，再进行新建环境重算 |

两边独立随机生成的窗口不能直接以随机值相同作为验收条件。本轮使用原厂实际保存后的等效技术设置，分别创建独立资料和密钥，比较真实网页结果；原厂对请求字段的自动规范化单独保留证据。

## 内核验收范围

支持的精确构建主版本为104、112、118、122、124、126、128、130、132、134、136、138、140、142、144、146、148、150、152、154、156。

21个内核均已完成原厂/本地运行对照、约65秒延迟存活、46项一致性及Cookie/LocalStorage关闭重开保存检查。最终代码另用21组全新的原厂窗口和全新的本地窗口比较首次生命周期：46项、附加权限、实际收到的6类HTTP请求头及网页内外4项尺寸均一致；DNT和Sec-GPC两边未发送，单独记录为缺失而非测得值。逐核结果见分层验收报告。

当前原厂7.2.0加载的一项内置扩展最低要求Chrome115，使104/112的原厂标准启动链超时。已用独立空资料重放完整启动参数确认原因；这两核以原厂精确内核、原厂有效签名及兼容扩展集合直启对照。其他19核通过正常原厂接口打开。报告区分这两种方法，不能把104/112描述为原厂标准接口已成功。

证据：`new-window-parity-matrix.json`、`new-window-parity-legacy.json`及`new-window-parity-acceptance.json`。修复前首次剪贴板差异的原始失败证据保留，不回写成通过。

## 登录期限修复与保护

原厂快照可能同时写`session:true`和有效未来期限；原厂实际采用该期限。原解析忽略未来期限，已修为优先采用明确有效期限并截到整秒。原厂对缺失/过期期限可能续一年，本地继续保留不延长已过期期限的原则。

旧资料只在身份、分区、安全标志及现值认证一致时，修复三个到期元数据字段；不把旧Cookie值回放到已使用窗口。存在额外DataProtect保护时，只复制Cookie库与Local State到离线空资料，借原生内核认证当前值及有效期上限。实际修改前备份，事务内重核完整原行，仅改期限、持久标志；保留`format:1`并增加`expiry_revision:2`，失败可重试且兼容旧版回滚。

21个内核各两轮验证真实会话Cookie、普通持久Cookie及同时带session提示和未来期限的Cookie，全部通过。104和148另做旧标记迁移，确认全部现值/密文不变、原生配置不变、二次准备不再修改，并完成两次正常重开。

证据：`all-core-cookies-final-parity.json`、`cookie-expiry-migration-native.json`。104/148还验证移动及自定首开尺寸、用户改尺寸后恢复、WebRTC配置与实际代理门禁一致、网络失败和出口改变拒开，见`parity-created-options-live.json`；该专项不等于已测试真实网站的全部WebRTC候选。

最终默认自检92项通过、0失败、0跳过；13份原有本地记录、资料、密钥、基线及随包文件只读检查通过。管理器已正常退出并显示新实例，加载修复后的代码。

本轮43个原厂测试窗口、49个本地合成记录均已删除；两个专项共清理11个测试目录，未删除用户资料、恢复备份或共用内核。保留加密证据与脱敏报告，自有测试浏览器主进程残留0。清理证据见`new-window-parity-cleanup.json`与`parity-auxiliary-cleanup.json`。

## 仍需明确的边界

- 以上是在本机、当前精确构建和所列信号中的真实验收，不等于所有硬件、所有网站、所有可观察信号都完全相同。
- 本轮未做第二台设备的平台登录验收；已有跨设备规则不扩大。
- 已导入窗口固定原指纹；新建随机样本分布不宣称等于原厂在线随机服务。
- 云端同步按要求跳过；其他已公开功能边界（代理商托管、UDP、二维码识别、跨系统字体等）仍见[本地窗口创建](本地窗口创建.md)。
- 通知关闭继续保留本地“阻止”语义，启动清理继续保留既有资料保护范围；未为了模仿原厂特殊分支改变这些已有开关的含义。
- 平台服务端到期、撤销登录或要求验证仍由平台决定；保存资料不代表绕过这些规则。
