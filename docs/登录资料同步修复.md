# 登录资料同步修复

2026-11-10复核补充：便携OSCrypt认证同时检查`Default/Network/Cookies`及旧位置`Default/Cookies`；两者并存时分别认证，任何一处错钥匙、未知密文、损坏或超出预算均拒绝。此步骤只读数据库，不延长Cookie有效期、不改变分区，不表示已定位真实账号掉登录原因。合成跨用户重新包装仍只改变`Local State`的同钥包装。

## 2026-11-09问题与原因

原来源在比特中保持登录，本地副本打开后显示“已登出”。此前仅验证完整文件复制、加密钥匙、环境基线和合成登录存储，没有验证原厂启动时的Cookie补写，因此不能证明真实来源已完整保留登录。

REA已提取的原厂主进程中，`Qf`读取窗口配置的`cookie`字段；128及更新版本经`$f/qp`先写`Default/~Cookies`，旧版本通过`ep`补写Cookie。这是窗口启动准备，不是单纯磁盘profile复制。旧导入记录虽然保留了该配置快照，却将`cookie_text`置空、`_cookie_pending`置否，没有将快照应用到浏览器。

现场对照确认来源磁盘Cookie与配置快照不完全一致。第10个窗口的原快照包含66条有效Cookie；补齐后，隔离副本实际平台返回对应账号信息，未重新登录，原来源和现有本地资料在诊断期间保持不动。仅“Cookie行数相同”或“没有登录按钮”不作为平台登录成功的证明。

## 修复方式

- 新来源在发布前完成启动Cookie恢复，仍保留整个来源profile和一对一来源绑定。
- 匹配内核在独立空profile中离线写Cookie；借用同一原生配置和OSCrypt钥匙，不改变DataProtect。通过CDP回读核对值及安全标记，正常关闭后，用相同数据库结构的事务合并加密行。
- 只合并明确的Cookie记录。标签会话、LocalStorage、SessionStorage、IndexedDB、密码和指纹基线不参与改写。不会为补Cookie先打开账号网站再重载。
- 来源的`expirationDate/expires/expiry`保持原到期含义；已过期记录不延长。会话Cookie在最终数据库仍是会话记录；分区键和跨站标记独立匹配。Schema、计数或事务失败明确停止。
- 旧副本先保存完整`backups/<窗口ID>-<随机标识>`备份，再一次性补齐。私有`_startup_cookies`标记成功后，普通重开不重复覆盖浏览器后来更新的Cookie。显式用户Cookie优先。
- 不新增依赖或常驻服务。额外空浏览器只在首次导入/旧副本修复期间运行，完成或失败均正常关闭；清理失败保留可识别资料并停止。共享源资料和其他窗口不动。

## 验证

- `tests/test_import_cookies.py`：输入格式、前缀/host-only、过期不续期、会话语义、事务回滚、Schema/计数拒绝、分区隔离、用户覆盖和幂等，纳入默认自检。
- `tools/verify_import_cookies.py --execute`：只接受带明确标记的独立测试包；21个内核分别完成原生加密Cookie合并、两次正式重开、会话Cookie/HttpOnly保留及同钥验证。第一次打开后更新Cookie，第二次不回退旧值。全部通过并清理合成资料。
- 现有10个窗口已检查和处理；9个有Cookie快照的窗口保存完整备份并补齐，1个无需补写。原生载荷、旧基线、OSCrypt密钥及其他profile文件逐项比对不变，来源profile未改。报告仅保存计数及布尔，不输出Cookie值、账号或代理参数。
- 修复后第10个实际窗口经正式`ManagerService.open`连续两次打开，平台页面均加载且返回对应账号的成功响应，没有“已登出”提示、没有重新登录。原生配置、基线和OSCrypt钥匙均保持原值。此现场结果限该平台/账号，不宣称其余账号已逐站验收。
- 21个内核的中文深目录路径专项也全部完成：每核原资源树超过Windows限制，实际进程使用同一实体短名；两次打开、确权、关闭及删除均通过。

平台仍可按自身规则使凭据到期或失效；此次修复针对遗漏的原厂启动恢复步骤，不修改平台有效期，也没有通过重新登录掩盖故障。
