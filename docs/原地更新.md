# 覆盖新版包，正常启动完成更新

本功能从v0.2.8便携包提供。用户只需覆盖完整新版包，再正常启动，不需要运行额外的更新或迁移脚本。现有v0.2.7 ZIP保留原样。初始支持来源是已核验的官方v0.2.7发行清单，升级要求新版本号高于旧版，不能把源码目录或同版本重新封装的包当作更高版本更新包。

## 用户操作

1. 正常关闭旧版全部浏览器窗口和管理器，等待退出。仅关闭管理器可能留下浏览器。
2. 将完整新版ZIP的内容覆盖到原程序目录。例如原目录为 `D:\LB`，新版的`启动本地浏览器.cmd`应直接替换`D:\LB`中的同名入口，`.program-packages`也放在该根目录下，不要额外套一层新目录。保留原目录的资料、密钥及已有内核，不要先删除原程序目录。
3. 等待解压全部完成，再双击原目录的 **启动本地浏览器.cmd**。入口自动校验新版、更新公开程序并启动管理器。窗口资料、配置、密钥及已有内核仍使用原位置。

如果解压未完成或新版载荷缺件，保留原目录，将**同一完整新版包**重新覆盖完整后正常启动。如果更新进程被强制终止，正常启动会先恢复可认证的未完成事务，再重试更新；首次安装中断也会核对已发布文件后续跑。未知、损坏或无法认证的恢复信息会保留并停止，不会创建新资料或新密钥冒充恢复。

同一完整包重复覆盖或更新成功后的重复启动会校验当前安装，不再执行版本升级。同版本重新生成的不同包不视为同一包，不能用来绕过版本和发行清单限制。旧的完整迁移及手动更新入口已停用。

## 包结构与资料位置

新版ZIP在根目录只提供正常启动CMD及`.program-packages/<包标识>`中的完整新版载荷。解压时不直接覆盖原`app`或`runtime`；启动器使用独立载荷内的Python执行准备工作，完成后仍运行原根目录下的`app/local_browser.pyw`。`app/data`和`app/local-engines`不会变成载荷内的新目录。

首次安装在干净目录中按发行清单建立正常程序布局；发现已有资料、未知公开文件或不匹配的恢复记录时停止，不将它当成空安装。正常启动仍依赖当前完整载荷，因此`.program-packages`必须随整个便携目录保留，不能只复制已经展开的`app`和`runtime`，也不要自行删除当前载荷。

## 保留与替换范围

| 内容 | 行为 |
|---|---|
| `app/data` | 不替换、不移动、不复制完整profile；现有目录密钥和签名身份只读核验。目录库和WAL只会被临时复制到有界隔离位置检查结构，正常收尾即移除副本。 |
| `app/local-engines` | 已有窗口的独立内核完全保留。 |
| `app/engines` | 升级时已有原始库存完全保留；新版需要的同路径库存必须与现有文件树一致，缺失或不同构建在替换程序前拒绝。干净首次安装才从载荷建立随包库存。 |
| 旧资料内的 `resources` | 保持原有适配资源优先规则，不为升级盲目删除或覆盖。 |
| 程序源码、界面、公开资源和工具 | 按新旧发行清单更新；仅移走旧清单已认证的废弃程序文件，未知活动模块会拒绝。 |
| `runtime` | 内容完全一致时保留；有变化时成套暂存和替换，避免新旧依赖混合。 |

磁盘需要容纳完整新版载荷及变更程序的暂存；运行环境有变化时，还需要完整新版runtime的暂存空间。旧程序备份通过同卷移动保留在`.program-update-backup-<标识>`，不会复制完整账号profile。当前不会自动删除历史载荷或程序备份。程序备份是更新故障恢复材料，不是完整账号备份，也不提供已使用新版数据后的任意降级功能。保留的故障事务可能包含校验时的加密目录库临时副本，应与原目录一起妥善保管。

## 可靠性机制

- 新旧版本号、完整发行文件及运行环境清单先核验；来源兼容策略把允许的旧版本绑定到其发行清单原始字节SHA-256，拒绝未知来源及降级。只有已安装清单与同一载荷完全一致时允许按当前版本正常启动。
- 根启动CMD与载荷包标识严格绑定。升级校验只允许这一个已认证入口在解压阶段被替换，其他旧公开程序仍须符合旧发行清单。载荷本身不能声明修改其他载荷、恢复备份或私有资料。
- 复用管理器同名互斥锁，并按可执行路径、命令行、资料路径检查进程。可读的执行路径属于旧目录时，即使命令行不可读也拒绝更新。
- 先持久保存旧入口和不可变恢复计划，再原子发布不导入业务模块的阻断入口。再次确认进程退出之后才替换其它程序，最终新入口最后发布。旧0.2.7自检绕过管理器互斥的竞态也由此阻断。
- 正常启动准备及程序入口均在业务初始化之前识别未完成更新；`--self-check`也受入口保护。公开文件校验失败时不进入账号服务。Python读取缓存的位置被重定向到不创建的随机路径，不能以`-B`代替防旧缓存措施。这里的完整性校验发生在业务初始化前，不是操作系统执行Python前的原生签名验证。
- 多文件替换通过 `.program-update`持久事务保护；失败尝试回滚程序，强制终止后可独立恢复。恢复路径从受信的新旧发行清单重建，不执行日志自报的任意路径或删除命令。
- 恢复先还原runtime和其它程序，验证后最后还原旧入口。文件占用、未知摘要、链接、恢复信息不完整等情况保留现场并停止；不强杀用户进程，不触碰资料目录。

这不是文件系统整体原子提交，也不承诺任意断电、介质损坏或恢复元数据损坏后都能自动恢复。恢复元数据写入未完成或发生损坏时，安全行为是停止并保留完整目录。正式发版仍需对实际新版包执行0.2.7升级验收；合成故障试验不能代替真实账号的长期登录验收。

旧0.2.7入口本身不认识事务标记：新版载荷解压阶段尚未替换旧`app`和`runtime`；事务的阻断入口发布前中断时，其他旧程序尚未改变。混合替换阶段由独立阻断入口保护，恢复最后才还原旧程序入口。根CMD继续指向新版准备流程，下一次正常启动可恢复并重试。不能把新版启动保护描述成已经追溯修改旧ZIP中的代码。覆盖前必须关闭全部程序，不能用运行中的旧实例验收更新成功。

## 实现与维护

- 正常入口由`tools/overlay_layout.py`生成；`tools/portable_bootstrap.py`负责校验载荷、首次安装、更新恢复及启动原目录程序。
- 内部事务：`tools/inplace_update.py`，只供启动准备调用；独立载荷使用自身Python运行，不替换正在执行准备工作的运行环境。不再提供独立更新CLI。
- 启动保护：`app/update_guard.py`、`app/local_browser.pyw`和启动CMD；完整检查不实例化ManagerService。
- 打包：`tools/build_release.py`将完整程序放入独立载荷并生成发行清单、包标识及`update-policy.json`；不把发行标记写入源码根。维护者应在每次发版前明确审核支持来源的版本和清单摘要，不能自动放宽到任意旧版。
- 初始数据兼容范围是已验证的v1便携标记与现有目录库结构，本工具不执行数据库或profile迁移。未来需要改变数据格式时，必须单独设计、验证迁移并更新兼容策略。
- 默认回归：`tests/test_update_guard.py`、`tests/test_inplace_update.py`、`tests/test_overlay_update.py`及`tests/test_portable_bootstrap.py`，以及发行构建、ZIP校验和目录边界测试，统一由`tools/check_project.py`调度。
- 历史强退与Windows占用证据保留在`analysis/inplace-update-20261112/`；它不属于默认批量执行范围。

开发前搜索并评估了[PyUpdater](https://github.com/Digital-Sapphire/PyUpdater)及[Squirrel.Windows](https://github.com/Squirrel/Squirrel.Windows)。前者已归档、当前仓库没有可确认的许可证字段，且面向PyInstaller；后者采用MIT许可证，但会引入独立的安装/打包体系，与现有嵌入Python便携目录不匹配。本次复用现有路径、清单、进程检查和加密能力，用标准库实现本项目的受控文件事务，没有引入新依赖或复制这些项目的代码。
