# 原地覆盖升级核查（2026-11-12）

本报告保留当时的裸覆盖风险与验证证据。后续已按本次发现实现受控原地更新源码，当前实现及限制见[原地更新](原地更新.md)；这不改变原始裸覆盖试验结论，也不表示现有v0.2.7 ZIP已更新。

## 结论

不复制账号资料的原地升级在当前目录架构上可行，但**当前不能把“新版ZIP直接合并覆盖旧目录”作为经过可靠性验收的升级方式**。干净包不包含账号资料，只说明正确的文件合并不会直接写入这些目录，并不证明覆盖完整、版本兼容或中断后可恢复。此前对直接覆盖的肯定建议缺少这些前提，应以本报告为准。

本次是风险核查：未修改产品逻辑、未执行真实资料迁移、未启动真实浏览器、未重新生成或替换便携包。证据脚本和脱敏结果位于 `analysis/overlay-audit-20261112/`。

## 实际核对及复现

- 对本机现有v0.2.7 ZIP核对发行校验和、全部成员的SHA-256及ZIP读取校验、发行清单和运行环境清单的一致性。2624个文件，运行环境清单2162项；包内没有 `app/data` 和 `app/local-engines`，包含 `app/engines/148`。
- 当前工作目录的公开应用文件与该ZIP没有内容差异；当前原始148内核清单也相同。因此本次不是从一个已知不同的历史发行版升级到新版的实际验收，不能据此承诺所有旧版及未来版本兼容。
- 在隔离合成目录中创建真实格式的目录密钥、签名身份及加密目录库，再模拟ZIP合并覆盖。资料树逐文件的内容摘要、大小、文件身份、修改时间不变；独立内核不变；目录密钥、签名身份及加密记录仍可读取。浏览器资料文件使用合成占位内容，没有账号或网站登录验证。
- 同一个实验确认：新版ZIP中的同名原始148内核会覆盖旧文件；额外的112库存会留下；旧Python模块及旧依赖会留下；旧资料内的适配资源继续优先于新版公开资源。
- 使用正式 `local_browser.pyw` 启动代码，替换业务初始化及界面为计数桩：即使发行清单声明的文件缺失，仍进入业务初始化和界面启动。此项证明启动门禁缺失，不是实际运行损坏程序或实际改写资料的实验。
- 合成同大小、同修改秒数的Python源码更新，保留旧时间戳字节码缓存，实际子进程加 `-B` 仍加载旧代码。该条件复现证明 `-B` 只禁止写缓存，不能作为清除旧缓存的保证；没有认定现有正式包已发生此问题。
- 最终默认项目自检118项通过、0失败、0跳过，其中775个Python单元测试通过；21项专项条件全部通过。逐项证据见 `analysis/overlay-audit-20261112/project-check.json`及 `results.json`。专项的成功表示上述事实和风险被正确验证，不表示裸覆盖安全。
- 全套检查曾发现非BMP路径夹具固定拼接长度不适用于本轮更长的项目隔离目录；已仅调整 `tests/test_launch_paths.py`按实际根路径计算测试字符数，保留“Python字符数小于260、UTF-16单位数至少260且正式门禁拒绝”的断言。产品路径限制没有改变；上述最终结果来自修正后的完整重跑。

## 必须解决的边界

| 风险 | 当前证据及影响 |
|---|---|
| 部分覆盖后仍尝试启动 | `启动本地浏览器.cmd:3-18`只检查三个入口存在；`app/local_browser.pyw:82-94`未校验发行和运行环境清单。漏文件、断电、文件占用或解压失败可留下混合版本；标题的新版本号不代表程序完整。 |
| 原始内核被替换 | 包含 `app/engines/148`；裸覆盖绕过 `app/engine_store.py:81-88`中不同build并存、旧build不可变的保护。仍直接引用旧库存路径的历史窗口可能因摘要变化无法打开（`app/browser_core.py:475-481`）。当前独立窗口主要依赖保留的 `app/local-engines`，不能把历史风险当作这些窗口已经损坏。 |
| 缺少版本兼容及降级门禁 | `VERSION`用于标题，目录库初始化没有发行版本兼容范围检查。现有建表和旧设置迁移并不等同于任意版本可互相升级或降级。只核对文件不覆盖资料，不能证明新代码理解旧数据。 |
| 废弃文件和依赖残留 | 合并不会移除新版已经不再包含的旧文件；运行环境可以出现新旧依赖混合。`-B`也不能保证不读取已有缓存。 |
| 部分程序资源保存在旧资料目录 | `app/configuration.py:21-24`和 `app/profile_model.py:23-24,54-55`保留旧资料资源优先。它们参与旧配置适配，不应为“更新程序资源”而盲目删除或覆盖；应逐版本确认继续保留还是显式迁移。 |
| 正式启动自检不是只读升级验证 | `--self-check`会构造 `ManagerService`；构造可建表、迁移旧设置、保存重定位结果，以及继续用户此前已确认的永久删除计划。具体见 `app/local_browser.pyw:69-73`、`app/window_store.py:51-55,83-125`、`app/manager_service.py:40-49`、`app/portable_paths.py:84-127`。这些正常业务行为不能用来证明失败更新尚未触碰资料。 |

## 满足目标的最小改进方向

需要提供受控的原地更新入口，更新账号资料所在目录的程序文件，无须复制完整profile。以下保护均是**待实现要求**，不能当作当前功能：

1. 在写旧程序前，独立校验完整新版包及运行环境；确认支持的来源版本、数据格式和原有内核引用，拒绝未知版本、降级及不兼容状态。
2. 确认当前目录所属管理器、浏览器和后台任务已正常退出，并持有更新互斥保护。只关闭管理器不足以证明浏览器已经退出。
3. 明确保护 `app/data`、`app/local-engines`及已有 `app/engines`。新增库存按完整构建身份并存，不替换已有build；保留旧资料内必要的适配资源。
4. 仅暂存、替换和保留回滚所需的程序文件；运行环境成套更换。只根据经过核验的旧发行清单处理废弃程序文件，不按“新版没有”删除未知内容或资料。
5. 在首个替换前持久记录更新状态，启动入口遇到未完成更新必须停止。全部文件校验成功才提交；中断或失败能够恢复程序。多文件复制不是一个整体原子操作，不能只依赖单个文件的原子替换。
6. 程序更新验证与首次业务启动分离。如果确需数据结构迁移，先单独备份目录库等必要小文件并验证迁移，不复制全部浏览器资料；避免先执行迁移或删除恢复，再认定更新包不完整。

这些保护只增加新版程序暂存及程序回滚所需空间，不要求复制已有全部账号资料；实际峰值空间和耗时须在实现后测量。最终仍须对明确支持的旧版本、文件占用、磁盘不足、部分写入、中断恢复、旧资源及原内核并存做验收，不能宣称任意版本或任意断电条件下零风险。
